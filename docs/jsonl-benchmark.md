# Large JSONL benchmark

The opt-in `pnpm bench` command generates fixture-derived Codex, Claude, Pi and Cursor CLI
transcripts in the system temporary directory, then measures Huihua's existing scan and JSONL
streaming APIs.
It is not part of `pnpm check` or the default test suite.
It never searches real
agent stores.
Generated files are removed at the end unless `--out` names a directory.

## Run it

Use Node 22.18 or later after installing the repository dependencies:

```sh
pnpm bench --sizes 64MiB,800MiB,1GiB --providers codex,claude,pi,cursor \
  --repetitions 2 --mode all --early-records 100 --timeout-ms 1800000
```

Sizes use binary units (`MiB` = 1,048,576 bytes; `GiB` = 1,073,741,824 bytes). `all` runs
`scan`, `events`, `stream`, `early`, and `abort`.
Run the accumulating snapshot API separately
only when memory is available:

```sh
pnpm bench --sizes 64MiB --providers codex --repetitions 2 --mode snapshot
```

The command prints JSON results to stdout and generation time/directory to stderr.
Pass
`--out /path/to/empty-directory` to retain generated transcripts and `manifest.json`; otherwise
the generated directory is cleaned automatically.
Each measured repetition runs in a fresh Node
child process. `--timeout-ms` applies to each child; the default is 1,800,000 ms (30 minutes).
There is no configured memory cap.
Worker failures and timeouts remain in the JSON output.
Pass `--cpu-profile-dir /tmp/huihua-profiles` to write one Node `.cpuprofile` per measured child.
Profiling adds overhead, so use those runs to find hot functions and keep unprofiled runs as the
throughput baseline.
CPU profiles use Node's `--cpu-prof` flag; omit `--cpu-profile-dir` when comparing a different
runtime.
Pass `--child-exec /path/to/runtime` to run measured workers under another compatible runtime;
the Node parent still generates the fixture files, and each selected runtime runs in a fresh child.
This is useful for runtime comparisons such as Node versus Bun.
Use a
smaller first run such as `--sizes 2MiB --repetitions 1` to check a machine and filesystem.

## What is measured

- **scan** times `sessions.scan()` with an explicit single-file root and a 16 KiB header budget.
  This is discovery/header inspection; it is not full-transcript parsing.
- **events** opens a known scanned reference before timing, then consumes `open().events()` to
  EOF without retaining events.
  Event count is checked against fixture-derived expectations.
- **stream** consumes `open().stream()` to EOF and counts record, event, and diagnostic frames
  without retaining frames.
  All three counts must match generator expectations.
- **early** consumes stream frames until the requested native-record count, then returns.
- **abort** consumes frames to the same count, aborts with an `AbortSignal`, and checks the
  expected cancellation plus resource closure where the OS exposes open file descriptors.
- **snapshot** times `sessions.read()` (the accumulating snapshot path); its memory is reported
  separately and it is intentionally excluded from the default matrix.
  A snapshot has no observable first frame, so `firstMs` is null for this mode.

Timing starts after scan and handle creation for parse workloads.
First-event/frame latency is
measured from consumption start.
Total time ends at successful EOF for full reads; early return
and cancellation report elapsed prefix time and do not claim EOF.
MiB/s and native records/s are
reported only for full file reads.
CPU is user plus system time from `process.cpuUsage()`, in
microseconds.
Peak RSS and heap used are the highest `process.memoryUsage()` samples from child
startup through completion, sampled every 100 ms and at both ends.
Short runs can have only start
and end samples; brief allocation or RSS spikes between samples can be missed.

Each provider template reuses native rows from its existing JSONL fixtures, with repeated fixture
IDs retained, one call/result pair per cycle, and representative padded messages/reasoning/results
where the format supports them.
The final message is extended to make the generated file exactly
the requested byte count.
Generated expectations derive from parsing one fixture cycle and the
header, and full-frame counts are checked before a run is marked valid.
Generation time is
reported separately from parse timing.

## Results and limits

The benchmark report below records exact generated byte sizes and generator-native record counts,
individual repetitions, and medians.
The Linux `/tmp` filesystem on the measurement machine was
tmpfs, so file data was memory-backed.
Generation precedes parsing and warms the operating system's
file cache; these are warm-cache measurements, not cold-cache measurements.
A fresh child isolates
runtime state but does not clear the filesystem cache.

These synthetic transcripts represent the fixture-backed schemas and record lengths, not the
distribution of any user's real sessions.
Throughput and memory reflect this machine, Node/V8, the
virtualized CPU, and its memory-backed filesystem.
Sampling can miss transient memory peaks, and
synthetic data does not measure filesystem latency, content diversity, malformed input frequency,
or the cost of downstream consumers.
No absolute speed threshold is implied.

## Baseline run: 2026-10-05

The final matrix used two repetitions for every provider, file size and workload.
It contains 120 successful child-process runs; all generated record/event/diagnostic expectations
validated, and no worker timed out or raised a runtime error.
Cursor's matrix was repeated separately after replacing a nonnative synthetic header with a valid
fixture-derived Cursor message; the report uses that corrected run.
The complete per-run JSON, including first-frame/event times, CPU time, peak samples and individual
counts, is in [jsonl-baseline-2026-10-05.json](benchmarks/jsonl-baseline-2026-10-05.json).

The exact target sizes were 67,108,864 bytes (64 MiB), 838,860,800 bytes (800 MiB), and
1,073,741,824 bytes (1 GiB).
Each generator cycle keeps its native call/result pair balanced and reuses fixture IDs.
Pi emits more events than records because a single message can emit reasoning and text events.

### Environment and command

The work ran on a separate Linux VM: Node v24.19.0, Linux 6.18.44 x86_64, AMD EPYC 9V74 with
five visible vCPUs and a four-CPU cgroup quota, 17.6 GiB visible RAM with a 16 GiB cgroup limit.
The temporary filesystem was an 8.8 GiB tmpfs.
The only per-child limit was a 1,800,000 ms timeout; there was no worker heap/RSS cap beyond the
16 GiB cgroup memory limit.
The available pnpm was v11.19.0 although this checkout pins v12.4.2; Corepack could not download
the pinned release in this environment.

The main generation pass took 66.31 seconds; the corrected Cursor-only regeneration took 21.21
seconds.
Generation is outside all parse timers.
The tested commands were:


### Early return and cancellation

The 1 GiB prefix runs each stopped after 100 native records.
Early-return repetitions took 3.32–5.15 ms across providers; cancellation took 4.26–7.27 ms.
Every run confirmed the source descriptor was closed on Linux.
Pi emitted 177 events before early return and 178 before cancellation; the other providers emitted
99 and 100 respectively.
Cancellation reported the expected `benchmark cancellation` reason.

### Snapshot API, measured separately

At 64 MiB, snapshot repetitions were Codex 0.80 / 0.76 s, Claude 0.84 / 0.83 s, Pi 0.70 / 0.69 s,
and Cursor 1.01 / 1.05 s.
Maximum sampled RSS / heap ranged from 340.9 / 211.4 MiB (Pi) to 389.4 / 249.0 MiB (Cursor).
Snapshots were not run on the 800 MiB or 1 GiB files: these APIs deliberately retain all records
and events, and the 64 MiB result already shows much higher memory than streaming.

### Assessment

At 800 MiB and 1 GiB, `events()` throughput ranged from 74.2 to 130.7 MiB/s, and full `stream()`
throughput ranged from 71.7 to 122.9 MiB/s.
For each provider, the 800 MiB to 1 GiB median time increase was about 1.22×–1.41× for a 1.28×
increase in file size; this variation is consistent with two-run noise, with no sustained nonlinear
slowdown.
Sampled peak streaming RSS was 100.4–122.3 MiB and heap was 33.4–44.8 MiB at 800 MiB–1 GiB,
compared with 77.9–82.7 MiB RSS and 15.1–19.4 MiB heap at 64 MiB.
Memory rose modestly as transcript size grew rather than tracking the full transcript in memory.
These results support efficient incremental reads for this fixture-derived workload on this VM;
they do not predict cold-disk behavior or every real transcript shape.

### CPU profile

Profiles were collected in separate 800 MiB runs, one repetition per provider and workload:

```sh
CI=true pnpm bench --sizes 800MiB --providers codex,claude,pi,cursor \
  --repetitions 1 --mode events --cpu-profile-dir /tmp/huihua-cpu-prof-events \
  --timeout-ms 1800000
CI=true pnpm bench --sizes 800MiB --providers codex,claude,pi,cursor \
  --repetitions 1 --mode stream --cpu-profile-dir /tmp/huihua-cpu-prof-stream \
  --timeout-ms 1800000
```

Across the four provider profiles per workload, sampled CPU time for `events()` was concentrated
in `parseNative` / `JSON.parse` (19.3%), the `ingestLines` loop (16.8%), V8 microtask scheduling
(10.7%), and the `optional()` object helper (9.0%).
For `stream()`, those accounted for 17.6%,
16.5%, 11.7%, and 8.0%, respectively. `Ingestion.emit` accounted for another 6.0–6.5%, while
JSONL framing in `jsonLinesFrom` accounted for about 3.5–3.9%; garbage collection was 3.6–3.7%.
These are sampled self-time shares aggregated across providers and identify likely constant-factor
targets, not the speedup an optimization would achieve.
The profile runs validated all expected
records, events, and diagnostics and reached EOF without errors.
The profiler adds overhead, so
profiled elapsed times are excluded from the throughput tables.

### Optimization experiments

After profiling, four low-risk hot-path changes were retained in `src/shared/jsonl.ts`:

- Check only the leading whitespace of nonblank lines instead of running a callback over every
  byte to decide whether the entire record is blank.
- Reuse a fatal UTF-8 `TextDecoder` instead of creating one for every native record.
- Parse a complete line directly from its read-chunk view when it does not cross a chunk boundary;
  lines spanning chunks still copy their parts so caller-owned/reused buffers remain safe.
- Increase the file read high-water mark from 64 KiB to 256 KiB.

The 64 MiB screening runs used three repetitions per provider and workload.
The first three changes
were noisy individually, so their small per-change percentages should not be summed.
The 256 KiB
read size had a consistent gain in full `stream()` runs, but it increased sampled RSS by roughly
15–40 MiB in these tests; 1 MiB chunks were often slower for `stream()` and used more RSS, so were
rejected.
The retained 256 KiB size was then checked on 800 MiB and 1 GiB.

#### Alternate runtime and parser attempts

The same benchmark parent and generated files can run under another executable:

```sh
CI=true pnpm bench --sizes 1GiB --providers codex,claude,pi,cursor \
  --repetitions 2 --mode events --child-exec /path/to/bun
CI=true pnpm bench --sizes 1GiB --providers codex,claude,pi,cursor \
  --repetitions 2 --mode stream --child-exec /path/to/bun
```

On the same VM, Bun 1.4.2 workers were compared with Node 24.19.0 workers using the same final
256 KiB reader.
The Bun version string reported through Node compatibility APIs was v26.3.0.
All 1 GiB repetitions matched record/event/diagnostic expectations and reached EOF.

| Provider | `events()` Node → Bun | Bun time reduction | `stream()` Node → Bun | Bun time reduction | Bun stream peak RSS |
| -------- | --------------------: | -----------------: | --------------------: | -----------------: | ------------------: |
| Codex    |         7.91 → 4.89 s |              38.2% |         8.85 → 5.44 s |              38.5% |            69.3 MiB |
| Claude   |         9.26 → 5.61 s |              39.5% |         9.54 → 5.97 s |              37.4% |            68.8 MiB |
| Pi       |         7.13 → 3.99 s |              44.0% |         7.43 → 4.54 s |              39.0% |            66.1 MiB |
| Cursor   |        11.35 → 7.06 s |              37.8% |        12.31 → 8.16 s |              33.7% |            69.7 MiB |

A separate streaming parser-only check over fixture-derived 64 MiB files showed Bun JSON parsing
about 1.50×–1.87× faster than Node for these small native records.
That does not account for the
whole application speedup: the 1 GiB end-to-end advantage also includes differences in runtime
streaming, async iteration, decoding, and object handling.
Huihua still declares Node as its
supported runtime; these numbers do not change that support contract.

Bun's `Bun.JSONL.parseChunk` API was also tested in a parser-only streaming pass.
It was 1.39×–1.73× faster than calling Bun `JSON.parse` once per line on these 64 MiB files.
However, it returns parsed values and a consumed-byte offset for a batch, rather than each native
line's raw text and byte position; that cannot directly preserve Huihua's per-record evidence and
diagnostic behavior.
No end-to-end Huihua result was measured for this API, so it was not adopted.
See Bun's [`parseChunk` API](https://bun.sh/reference/bun/JSONL/parseChunk).

`simdjson_nodejs` was installed only in `/tmp` and substituted temporarily for `JSON.parse`.
Its
`parse()` converts the C++ representation to ordinary JavaScript objects, and took 2.9–4.1× as long
as Node's native parser in the 64 MiB `events()` and `stream()` tests.
Its lazy result does not expose the ordinary
object/array access used by the provider adapters.
It was rejected and is not a project dependency.
A `Buffer.isUtf8` plus `Buffer.toString()` decode path was also tested; results ranged from 10% slower
to 2% faster across providers, so the existing fatal `TextDecoder` semantics were retained.
Reusing one shared empty object in the `optional()` helper and a 128 KiB read buffer did not produce
a consistent improvement; 1 MiB read buffers regressed `stream()` and increased sampled RSS.
Fastify's [`fast-json-stringify`](https://github.com/fastify/fast-json-stringify) is an output
serializer, while [`secure-json-parse`](https://github.com/fastify/secure-json-parse) focuses on
prototype-poisoning defenses; neither was a faster drop-in parser for this reader.
